## 1. はじめに（動機）

今回ランサーズのサービス内にある「よくあるお問い合わせ」ページをハイブリッド検索に刷新しました。
なぜFAQなのか
これによりユーザーにも、AIにも、サービスにも嬉しい結果になった

### 1-1. これまで（改修前）

`Faq::getFaqSearchResult()` — これが FAQ 検索のすべてだった。

```php
$keywords = preg_split('/[+\s]+/', $keyword);
$cond = ['Faq.close' => 0];
foreach ($keywords as $value) {
    $cond[] = ['OR' => [
        'lower(Faq.description) LIKE' => '%' . $value . '%',
        'lower(Faq.title) LIKE' => '%' . $value . '%',
    ]];
}
return $this->find('all', [
    'order' => ['Faq.display_order' => 'ASC'],
]);
```

ここから言えること（記事で効くのは全部これ）:

- **スコアリングが存在しない。** 並び順は `display_order ASC` のみ。
  つまり「一番関連するFAQ」ではなく「一番前に置かれたFAQ」が1位に来る
- スペース区切りの **AND**。語が増えるほどヒットが厳しくなる
- `LIKE '%語%'` なので**部分一致だけ**。
- 形態素解析なし
- 表記ゆれ吸収なし
- 同義語なし
- 全角半角と大小文字だけは吸収していた。
  逆に言うと**それしかしていない**

- `faqs` テーブルに FULLTEXT インデックスは無し（`faq_category_id` の INDEX だけ）

### 1-2. 3つの動機（この順で並べると「AIのため」「人間のため」「コスト」が揃う）

1. **AIチャット（Anna）が該当FAQに辿り着けず、トークンを無駄にしていた**
   - 社内AIチャットに同じFAQ検索を引かせる計画だった。`/api/v1/ai_chat/faq/search`
   - AIは検索結果を文脈に入れて回答を作るので、**関連度順でないリストを渡すと、
     関係ないFAQ本文がそのままコンテキストを食う**
   - 「AIに検索させる」と決めた瞬間に、スコアリング無しの検索が実害になった
  ランサーズはAIチャットを提供しています。
  これはAgentic RAG 方式をとっており、質問に対して、AI（LLM）がFAQ検索などをループ処理して回答に必要な情報を集めます。
  ここでもFAQ検索の精度がAIチャットの回答精度に影響してきます。
  欲しい情報が見つからないと何回も検索キーワードを変えて再検索を繰り返すので、その分時間もかかり、コンテキストも食います。
2. **専門用語と完全一致しないとヒットしない**
   - 部分一致AND なので、ユーザーの言い回しがサイト側の用語と1文字でもズレるとヒットしません。
   - 人間の使い勝手としても悪かった
3. **サポート問い合わせコストの削減**
   - 自己解決率が上がれば問い合わせが減る、という投資判断の側面

### 1-3. どれくらいダメだったかの数字

- LLM生成の評価クエリ300件で、**LIKE の hit@10 は 3.7%**（MRR 0.035、miss 289/300）。
  **96%のクエリで、正解FAQがtop10にすら出てこなかった**
- PoC初期の代表5クエリの定性確認では、**5件中3件が現状ゼロ件**。それがハイブリッドで全部正解を引けた

> 書き方の注意: この 3.7% は「LLMが生成した自然文クエリ」での数字。
> 後にGA4の実クエリで測り直したら LIKE は hit@1 38.2% まで上がっている（実クエリは単語が多いのでLIKEでも当たる）。
> **記事Aで「96%が空振り」と書くなら「自然文で聞いたとき」と条件を添える**のが安全。
> 条件を書きたくないなら、数字ではなく「スコアリングが無い」という構造の話にとどめる。

## 2. ベクトル検索を入れたいが、環境がモダンではない

ベクトル検索を導入したいと思い立ちましたが、実装環境が壁になりました。

### 2-1. 制約の実態

| 項目 | 実際 |
|---|---|
| 検索基盤 | **Elasticsearch 7.12**（実態は AWS OpenSearch Service 上の ES 7.10） |
| ベクトル検索 | **kNN 非対応。`dense_vector` + kNN の GA は ES 8.0 から** |
| アプリ | **CakePHP 2.8**（`cake28/` ディレクトリで運用している） |
| 既存の日本語処理 | kuromoji + Sudachi のアナライザー設定は入っている |
| ESの用途 | プロジェクト検索 / ランサー検索 / ポートフォリオ検索 / メッセージボード検索 / 各種サジェスト |

**「ESはあるのにベクトルが使えない」** という状態。ここが効く。
ESが無いなら「入れるか」の話になるが、**あるのに世代が足りない**ので、
選択肢が「上げる」か「使わない」の二択になる。

### 2-2. 上げられない理由（ここを書かないと「上げろよ」で終わる）

ESクラスタを上げるということは、FAQ以外の全部を巻き込むということ。

- 既存 **7インデックス**（プロジェクト / ランサー / サジェスト / タグサジェスト / ポートフォリオ / ボード / フォローユーザー）
- さらに Firehose 経由の `insight-logger` も同じクラスタに乗っている
- つまり移行の本体は「FAQのベクトル検索」ではなく **「7機能＋ログ基盤のインフラ移行と全機能の回帰検証」** になる

**FAQをトリガーにやる仕事ではない。** ここが判断の芯。

## 3. 4案を比べて、新規インフラゼロを選んだ

今回はMySQLと自前のベクトル計算を実装する方針を採用しました。

判断の鍵となったのはデータの規模でした。

### 3-1. 比較表（記事にそのまま置ける）

| 案 | 概要 | 採否 |
|---|---|---|
| A | FAQ専用に別のES 8.xを新設 | × 検索基盤が二重になる |
| B | ESクラスタ全体を8.x / OpenSearch 2.xへ上げる | × FAQをトリガーには重すぎる（上記7機能＋ログ基盤） |
| C | ES 7.12のまま、外部embeddingをアプリ側で統合 | × ESと自前融合の二重管理が負債化する |
| **D1** | **MySQL FULLTEXT + 自前cosine + RRF。ESを使わない** | **◎ 採用** |

### 3-2. 判断の根拠は「規模の実測」だった（記事の肝はここ）

dev環境で先に測った（2026-05-14時点）:

| 項目 | 値 |
|---|---|
| faqs 総数 / 公開（close=0） | 920件 / **785件** |
| faq_categories | 120件 |
| 平均本文長 / 最大本文長 | 560文字 / 6,952文字 |
| 公開分の本文総量 | **約44万文字** |

**785件・44万文字。** この数字が出た時点で判断が決まった。

- この規模なら **exact な全件cosineで足りる**。ANN（HNSW等）は要らない
- embeddingの**全件再生成が一瞬**（後述: 13秒・$0.003）。作り直しが怖くない
- つまり **スケール由来の制約がほぼゼロ**なので、技術選定は「正しく作れるか」だけで決められる

> ここは「小さいことは弱点ではなく、選択肢を増やす」という書き方ができる。
> 記事の主題（レガシー環境）と噛み合う一番いい部分。

### 3-3. 唯一増える依存

新規インフラは足さないが、**Gemini API（外部embedding）への依存だけは増える**。
これは Searcher 内で BM25単独フォールバックできる設計にして受け入れた（§4-5）。

## 4. 手持ちの道具だけで作る

「MySQL・PHP・Redis しか使っていない」を具体で見せる節。

### 4-1. BM25 = MySQL FULLTEXT（ngram parser）

`faqs` に FULLTEXT インデックスを1本足しただけ。

```sql
FULLTEXT KEY `ft_faq_search` (`title`, `description`) /*!50700 WITH PARSER `ngram` */
```

検索SQLはこれだけ。

```sql
SELECT id, title,
       MATCH(title, description) AGAINST(:q1 IN NATURAL LANGUAGE MODE) AS score
  FROM faqs
 WHERE close = 0
   AND MATCH(title, description) AGAINST(:q2 IN NATURAL LANGUAGE MODE)
 ORDER BY score DESC
 LIMIT :topk
```

- **日本語なので parser は ngram**（kuromoji等の形態素解析器はMySQL標準にはない）
- `IN NATURAL LANGUAGE MODE` の `MATCH` スコアがそのままBM25相当のランキングになる
- `close = 0` はSQLのWHEREで必須化（非公開FAQが混ざらないことをDB層で担保）
- レイテンシは **BM25単独で p99 0.38ms**

### 4-2. ベクトルの置き場 = MySQLのBLOB列

専用のベクトルDBは立てない。テーブルを1本足しただけ。

```sql
CREATE TABLE `faq_embeddings` (
  `faq_id`    int NOT NULL,
  `model`     varchar(64) NOT NULL,   -- 例: gemini-embedding-2
  `dim`       smallint unsigned NOT NULL,
  `embedding` blob NOT NULL,          -- pack('f*', $floats) で詰めたバイナリ
  `updated`   datetime NOT NULL,
  UNIQUE KEY `uq_faq_embeddings_faq_model` (`faq_id`, `model`),
  CONSTRAINT `fk_faq_embeddings_faq` FOREIGN KEY (`faq_id`)
      REFERENCES `faqs` (`id`) ON DELETE CASCADE
);
```

- **float32のリトルエンディアン連結**。PHPの `pack('f*', $floats)` で詰めて `unpack('f*', $blob)` で戻す
- 768次元 × 4byte = **1件3,072バイト**。785件で **2.3MB**
- `(faq_id, model)` のUNIQUEで**複数モデルを並存**させられる。
  → これが後で効く。OpenAIとGeminiを同じテーブルに同居させて比較できた
- `ON DELETE CASCADE` なのでFAQを消せばベクトルも消える

### 4-3. cosine = PHPのforループ

ライブラリなし。これで足りる。

```php
public static function cosine(array $a, array $b): float
{
    $len = min(count($a), count($b));
    $dot = 0.0; $na = 0.0; $nb = 0.0;
    for ($i = 0; $i < $len; $i++) {
        $dot += $a[$i] * $b[$i];
        $na  += $a[$i] * $a[$i];
        $nb  += $b[$i] * $b[$i];
    }
    $denom = sqrt($na * $nb);
    return $denom <= 0.0 ? 0.0 : $dot / $denom;
}
```

**公開FAQ全件（785件）とのcosineを毎回まわして 44ms。** これで十分だった。

### 4-4. 次元数は測って768にした（4倍速の話）

Geminiの既定は3072次元。MRL（Matryoshka）で縮約できるので、実際に測って決めた。

| 次元 | hit@1 | hit@5 | MRR | cosine全件 | 総容量(785件) |
|---|---|---|---|---|---|
| 256 | 57.3% | 83.0% | 0.683 | 14.9ms | 0.8MB |
| **768（採用）** | **61.7%** | 85.0% | 0.721 | **44ms** | 2.3MB |
| 1536 | 61.3% | 86.3% | 0.723 | 85ms | 4.6MB |
| 3072（既定） | 62.3% | 86.7% | 0.728 | 173ms | 9.2MB |

**768は3072とほぼ同品質（hit@1 −0.6pt）で、cosineが4倍速い。**
「全件cosineでいい」という設計は、次元を落とせば落とすほど効く。

### 4-5. 融合 = RRF（これも自前の純関数）

```
score(d) = Σ_i  w_i / (k + rank_i(d) + 1)
```

- `k = 60`（RRFの標準値）
- 重みは **等重み `[1.0, 1.0]`**
- 同点は **id昇順**で安定化（`arsort` は同値の順序が不定なので `usort` でタイブレーク）
- スコアの絶対値ではなく**順位だけ**を使うので、BM25スコアとcosineの
  **スケールを正規化しなくていい**。ここがRRFを選ぶ実務上の理由

### 4-6. キャッシュ = 既存のRedis

新しいミドルウェアは足していない。

| 対象 | TTL | キー |
|---|---|---|
| doc embedding 全件マップ | **+1 hour** | `lancers.faq.embedding.doc.{model}.{dim}` |
| query embedding | **+30 minutes** | `lancers.faq.embedding.query.{model}.{dim}.{query}` |

- **キャッシュキーに `dim` を含めてある**ので、次元を変えてデプロイしても
  古いキャッシュと衝突せず、勝手に別キーになって古い方はTTLで消える。地味に効く設計
- リクエスト内ではさらにインスタンス変数で持って、Redis往復を1リクエスト1回に抑える

### 4-7. フォールバック = Geminiが落ちてもBM25で出す

**外部依存はGemini APIだけ**なので、そこだけ守れば止まらない。

```php
$bm25 = $this->searchBm25($query, $perSource);
try {
    $vector = $this->searchVector($query, $perSource);
} catch (FaqEmbeddingException $e) {
    // ログとDatadog spanにタグだけ残して、BM25単独をそのまま返す
    return array_slice($bm25, 0, $topK);
}
return $this->fuseRrf([$bm25, $vector], $topK, self::DEFAULT_RRF_K, [1.0, 1.0]);
```

- `source` は `hybrid` にせず **`bm25` のまま返す**（何が起きたか結果側で分かる）
- BM25側の例外はDB障害なのでフォールバックせずそのまま投げる
- ログにクエリ文字列とembedding値は出さない

### 4-8. ★このフォールバックが牙を剥いた話（記事に入れると強い）

pre環境の検証で、**HTTP 200・関連FAQも返る。でも全件 `source: "bm25"`** という状態になった。
つまり**サイレントに劣化していた**。しかも応答181msと速い。速いのが異常の兆候だった
（Vectorが効いていればAPI往復で数百ms出る）。

- 真因は、検証用ブランチが古くて、**認証ファイルをイメージに焼く変更を取り込んでいなかった**だけ。
  製品コードのバグではなかった
- 厄介なのは切り分け手段。catchして200を返すので**ログにもレスポンスにも出ない**
- 解決策: **catch の中で dd-trace の span にタグを立てた**
  （`faq_hybrid.vector_fallback` / `error_kind` / `model`）。
  さらに `set_priority_sampling(USER_KEEP)` でサンプリングに埋もれないようにして、
  Datadogで `@faq_hybrid.vector_fallback:true` を引いて確定した
- **教訓: 良いフォールバックほど、落ちたことが見えない。フォールバックを実装したら
  同時に「発動したことを観測する経路」も作る。**

これは恒久計装として残していて、本番のフォールバック率アラートに使っている。

### 4-9. 編集追随（軽く触れる程度でいい）

- 一括indexing: batch側のコマンドを手動/日次で実行
- 編集追随: 管理画面で保存 → キューに `faq_id` だけ投げる → 常駐ワーカーがDBから最新を読んで再生成
- **本文をメッセージに載せない**のがポイント。consumer側で読み直すので連続編集の順序狂いを吸収できる
- 実測で**編集保存から約1秒**で `faq_embeddings` が更新される
- コストはキュー込みで**月数十円規模**
